01 / YOUR FILE STAYS IN THIS BROWSER

Analyze a saved network capture

Use only captures from your own device or a network you have permission to inspect. A capture can contain private addresses, names and payloads.

Classic PCAP 2.4; Ethernet, raw IPv4 or Linux cooked v1; up to 20 MB / 100,000 packets. TCP, UDP and basic UDP DNS. No PCAPNG, IPv6 decoding, TLS decryption or live capture.

How do I get a compatible file?
  1. On your own computer, open Wireshark and select the network interface you are allowed to capture.
  2. Capture briefly while reproducing your problem, then stop. Do not capture other people's traffic without permission.
  3. Use File → Save As and choose the classic Wireshark/tcpdump PCAP format, not PCAPNG. Changing the filename extension is not conversion.
  4. Open the saved file here. No file contents are uploaded. Close the tab or Clear file when finished.

This page is not a Wireshark replacement. Use Wireshark for full protocol dissection. No background packet collection runs here.

    02 / REAL READ-ONLY API CHECK

    Can public DNS resolve this domain?

    If a site name does not resolve, the connection cannot begin. Compare an actual Google Public DNS response with the historical DNS evidence in your file.

    Clicking Check DNS sends only this domain to Google Public DNS through AETHER's server. No packet file, filename or capture findings are sent. No AI is involved. Do not enter private internal names.

    What does this API check prove?

    It reports the A-record answer seen by Google's public resolver at lookup time. It does not check your device's configured DNS, website availability, Wi-Fi quality, link capacity or the cause of every internet problem. A successful response with no A records is different from an error. Cached responses are labeled. IPv6-only sites may have no A record.

    The read-only AETHER endpoint is /api/dns-check?name=example.com. The response below shows the actual JSON. Lookup data can be cached for 60 seconds. Global limit: 12 upstream checks per minute.

    Try a safe troubleshooting story

    1. Load the clearly labeled sample and find its DNS failure and TCP resets.
    2. Explain the evidence and the next checks, not a guessed root cause.
    3. Check example.com with the real DNS API and inspect its JSON.
    4. Download the redacted report. Use the separate simulation lab only to demonstrate hypothetical routing/policy changes.

    The sample is synthetic. A real user-supplied capture is real file evidence, but still has capture-point and protocol-coverage limits. No automatic bridge from packet findings to simulator topology exists.
